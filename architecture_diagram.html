AWSHarnessLoopEngineering — Architecture Diagram

Multi-agent customer-service harness · AWS Bedrock AgentCore · Source: AWSHarnessLoopEngineering/

What happens on a cache miss in this service? PROVEN FROM CODE

  1. A customer utterance arrives at Amazon Connect and is forwarded to the Bridge Lambda (lambdas/bridge/handler.py). The bridge validates the event (utterance ≤ 4096 chars, contact_id ≥ 33 chars) and enforces a per-session invocation rate limit (lambdas/bridge/rate_limiter.py).
  2. The bridge invokes the Supervisor Harness (AgentCore, configured by config/harness/supervisor.yaml). The supervisor classifies the intent and routes it. If the intent is a knowledge / product question it delegates to the Tech Support Worker via lambdas/delegate_technical_support/handler.py (shared/routing.py → RoutingOutcome.DELEGATE_TECHNICAL_SUPPORT).
  3. The Tech Support Worker calls the knowledge_retrieval Lambda (lambdas/knowledge_retrieval/handler.py) as a tool. This Lambda issues a bedrock-agent-runtime.Retrieve() call against the Bedrock Knowledge Base — this is the actual KB read that can miss.
  4. The Bedrock Knowledge Base executes a semantic vector search against the OpenSearch Serverless collection (VECTORSEARCH, 1 024-dimension Titan Embeddings V2 index). The query is embedded on the fly by the Titan model; matching chunks are returned with a relevance score. There is no application-level cache between the Lambda and the KB API — every call is a live vector search; "miss" here means no chunk scores ≥ 0.5.
  5. The tool enforces RELEVANCE_FLOOR = 0.5 (shared/tools.py). Every result scoring below the floor is silently dropped before the model sees anything.
  6. If zero passages survive the floor → the tool returns NoRelevantDocumentation. The Tech Support Worker surfaces a phrase-table message to the customer; it never fabricates an answer (Requirement 5.4).
  7. If mid-pagination a continuation call fails or the 12-second budget (KB_RETRIEVAL_BUDGET_S) expires but at least one passage was already retrieved → the tool returns PartialDocumentation, sending the surviving passages plus an unavailability notice (ErrorCategory from shared/error_taxonomy.py). This prevents a worse outcome of discarding good content because a later page call failed (Requirements 5.7, 16.4).
  8. If no passages were retrieved before the failure → the tool returns ToolFailure. The Tech Support Worker offers a follow-up: lambdas/followup_trigger/handler.py registers a case in the FollowUpCases DynamoDB table and returns a case_reference validated against CASE_REFERENCE_PATTERN (shared/case_reference.py).
  9. In all failure paths the Bedrock Guardrail (shared/guardrail.py) is consulted to ensure the final text meets RAI constraints before it is returned to the Bridge Lambda, which formats the response back to the Connect Contact Flow.
